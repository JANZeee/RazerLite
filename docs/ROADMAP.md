# RazerLite 后续开发计划

> 当前安排已更新为 [2026-10-22 下一阶段开发计划](NEXT_DEVELOPMENT_PLAN.md)，以 0.9.2 为基线并补充最新上游调研。本文件保留历史计划与执行背景，未完成内容以新计划为准。

制定日期：2026-10-19。基线：0.8.1 / build 10。当前没有外设可供连接；本文件是开发计划，不表示下列功能已经实现。本轮核对代码、既有测试日志和验证记录，没有重新执行硬件查询。

执行进度：已交付 [0.9.0 离线场景](PHASE09_OFFLINE_SCENARIOS.md)、[0.9.1 独立档案库](PHASE091_LOCAL_LIBRARY.md) 和 [0.9.2 设置与菜单栏](PHASE092_PREFERENCES.md)。0.9.2 的登录重启与状态栏菜单验收仍单独保留；下一开发阶段为 0.10.x。下文保留制定时的基线与各阶段完成条件。

## 1. 目标与当前起点

下一阶段的目标是：让 RazerLite 在设备未连接时也能管理本地配置，并让开发与界面验收不再依赖外设；之后再逐步扩大经过验证的设备功能。继续保留 SwiftUI、系统框架、本地保存和事件驱动的实现。

| 现状 | 已有证据 | 后续缺口 |
| --- | --- | --- |
| 通用设备发现 | USB / Bluetooth HID 枚举、多接口聚合、热插拔、未知 PID 显示 | 不同设备、系统版本及真实重连场景仍需增加样本；系统不可见的设备不能保证发现 |
| 273 条型号目录 | 名称与 PID 参考、搜索 | 与实际适配状态尚未形成统一、可追溯的兼容性视图 |
| Viper V4 Pro `1532:00E6` USB | 电量、DPI、回报率配置有真机读取记录；一次明确授权 DPI 写入与读回成功 | 充电状态尚待本机验证；跨重启持久性及不同固件未确认 |
| BlackWidow `1532:02D2` USB | 电池与充电试读代码、严格匹配、模拟测试 | 尚未完成 macOS 真机查询与输入共存验收 |
| 蓝牙系统电量 | `BSK MOBILE` 曾成功发现并读取 macOS 系统电量 | 属于系统发布的数据；其他型号与私有 DPI/RGB 协议未获验证 |
| 本地 DPI 档案 | 保存、选择、导入、导出、删除；schema 1 | 入口依附于已连接设备；缺少独立离线管理、重命名与复制 |
| 原生界面 | 无设备页、目录、设置等已检查 | 浅色、紧凑窗口、设备详情全状态及部分原生弹窗仍有验收缺口 |
| 工程验证 | 最近日志为 102 项测试 / 22 个 suite 通过；Release 与本地签名通过 | 不等于真机兼容性或公开发布验收；性能样本需要更新 |

代码中值得优先改进的具体位置：

- `Sources/RazerLite/App/RazerLiteApp.swift`：现有 Debug smoke 路径要求真实设备，场景不足；渲染入口尚未覆盖全部新增读取状态。
- `Sources/RazerLite/UI/Profiles/ProfileLibraryView.swift`：档案页依赖 `DeviceInfo`，离线时无法方便管理已有预设。
- `Sources/RazerLite/UI/SettingsView.swift`：外观、关闭窗口等主要是固定说明，尚未提供可持久化选择。
- `Sources/RazerLiteCore/Core/DeviceManager/DeviceManager.swift`：不同功能重复维护请求、忙碌、失效和清理状态，继续增加适配器会增加维护成本。
- `Sources/RazerLiteCore/Core/HIDTransport/HIDFeatureTransport.swift`：同步 IOKit 调用运行在公共串行队列；逻辑取消无法中断已经进入驱动的调用，需要如实反映限制。
- `README.md`：诊断说明仍混有 schema 4/5 的历史描述；后续整理当前能力摘要与历史验证记录。

## 2. 里程碑与依赖

版本号为建议安排，可按实际工作量拆分；以验收完成为发布条件，不预先承诺日期。

| 顺序 | 建议版本 | 交付结果 | 无外设能完成的范围 | 规模 |
| --- | --- | --- | --- | --- |
| 1 | 0.9.0 | 离线场景工具与完整界面验收 | 全部软件工作 | 中 |
| 2 | 0.9.1 | 独立本地档案库 | 全部软件工作 | 中 |
| 3 | 0.9.2 | 可保存设置、菜单栏整理、性能基线 | 设置和无设备性能可完成；登录重启另验收 | 中 |
| 4 | 0.10.x | 适配证据统一、读取生命周期收敛 | 结构与模拟测试可完成；兼容性结论待真机 | 中至大，分次交付 |
| 5 | 0.11.x | 已有设备验证与首个新增硬件功能 | 可先审查协议、建立测试；功能发布依赖硬件 | 由协议与硬件证据决定 |
| 6 | 1.0 | 明确兼容范围的可分发版本 | 可先准备脚本、文档；签名与跨机测试另有依赖 | 中 |

推荐执行顺序：0.9.0 → 0.9.1 → 0.9.2 → 0.10.x。外设恢复可用时，插入已有读取功能的真机验收，不必等待全部结构改进结束。1.0 的范围是公布清楚的已验证功能，不以支持所有雷蛇型号、全部 RGB 和宏为前提。

## 3. 0.9.0：没有外设也能验收真实界面

**用户收益：** 后续界面修改可覆盖设备页、错误页和菜单操作，减少只有连接外设时才发现的问题。

任务：

1. 增加 Debug 专用场景入口与固定测试数据，注入现有发现、读取及控制服务接口；复用正式 SwiftUI 页面。
2. 场景至少覆盖：无设备、仅鼠标、仅键盘、蓝牙系统电量、未知 PID、两台同型号设备，以及读取中、部分成功、失败、断连后重连、睡眠恢复。
3. 补充容易显示错误的数值：0% 电量、未知电量、X/Y 不同的 DPI、长设备名称、没有固件信息、只有接收器可见。
4. 预览使用独立临时档案库与设置存储；不得加载或改写用户的正式档案。
5. Debug 场景必须注入完整假服务，缺失依赖时直接失败，不能回退到 `NativeHIDFeatureTransport` 或系统蓝牙扫描。场景标识为“模拟数据”，不输出真机验证记录。
6. DPI 确认页可使用假控制服务验收取消、过期、失败与读回差异；模拟成功不计入设备能力证据。
7. 调整文字层级、长文本截断、空白与滚动；常用页面只保留当前状态和下一步操作。协议细节放在设备信息或展开项。
8. 检查键盘焦点、Tab 顺序、按钮无障碍名称、颜色以外的状态提示，以及辅助功能中的减少动态效果设置。

验收：

- 浅色 / 深色，默认窗口与当前最小窗口 960×640，页面没有关键内容遮挡、溢出或不可操作按钮。
- 固定场景能重复进入；改变设备或请求状态后，页面、菜单栏和错误提示一致。
- 测试验证假服务调用与状态变化；预览启动和交互不会创建真实 Transport。
- 原生窗口、菜单和弹窗另做交互验收；组件渲染截图仅作为布局证据。
- 保留已有回归测试、Debug / Release 构建与签名检查结果，不以增加测试数量作为目标。

交付物：场景入口、测试数据、界面修正、验收矩阵及截图、可运行 0.9.0。

## 4. 0.9.1：独立本地档案库

**用户收益：** 没有接收器时也能整理“办公 / 游戏”等预设，连接设备后再选择并确认应用。

任务：

1. 侧栏增加“本地档案”，使已有预设的查看、搜索、重命名、复制、删除、导入与导出独立于设备连接。
2. 允许为已定义的 Viper DPI 目标手动创建本地预设；明确这是输入的目标值，不是设备当前读数。
3. 保留现有范围与步进验证，暂不扩大到未经验证的型号、全部 DPI 档位表、灯光或按键配置。
4. 服务按 `ProfileDeviceTarget` 操作本地数据；仅在“载入设备编辑器”时要求匹配当前连接。相同型号有多个接收器时，明确选择目标会话。
5. “已选本地预设”“编辑器目标”“已读设备值”“本次应用读回结果”分别显示，避免把选择预设理解为应用成功。
6. 尽量保持 schema 1；若确需升级，先增加旧格式读取和迁移测试。损坏文件与未来 schema 保留原文件并反馈错误。
7. 导入增加文件大小与条目限制、冲突摘要；先验证全部内容，再写入本地库，失败不得部分污染。
8. 验收原生导入/导出面板的取消、错误路径、无权限目录和重名行为。新增纯本地操作不调用 HID 服务。

验收：

- 零外设条件下完成创建 → 重命名 → 复制 → 导出 → 重新导入 → 重启读取。
- 旧档案及当前选择仍可读取，冲突不悄悄覆盖；使用临时目录完成破损文件和写入失败测试。
- 未连接、连接方式不同或匹配歧义时无法应用。
- 选择、导入和应用重启均不自动提交设备设置；原有“检查变更 → 明确确认 → 整表读回”继续保留。

交付物：独立档案页、本地服务扩展、数据兼容测试、可运行 0.9.1。

## 5. 0.9.2：设置、菜单栏和资源占用

**用户收益：** 设置真正可用，菜单栏更易读，后台资源消耗有可复查的依据。

任务：

1. 增加 `AppPreferences`，支持跟随系统 / 浅色 / 深色，并在窗口、设置和相应菜单呈现中一致生效。
2. 支持关闭主窗口后保留菜单栏或退出；默认保持现有行为，退出时停止服务并使未完成计划失效。
3. 记住上次普通页面和窗口状态；不持久化失效的 registry 会话 ID，不恢复待确认写入许可。
4. 菜单栏优先显示设备名、电量和打开详情入口；读取时间、来源及错误放入设备子菜单。开启菜单本身不读取设备。
5. 整理当前版本的说明、诊断 schema 和兼容性摘要，历史数字保留在对应验证记录中。
6. 加入“登录时启动”的服务封装与状态显示：默认关闭，由用户开关触发注册。采用 macOS 13+ 的 `SMAppService`，从系统状态显示开启、需批准或失败，不能只保存一个布尔值。[Apple API](https://developer.apple.com/documentation/servicemanagement/smappservice)
7. 登录项验收前先解决应用安装位置：目前真实 bundle 在可清理缓存目录。准备稳定安装位置与更新流程后，再验证退出、登录和重新启动。登录启动仅启动发现与界面服务，不自动下发配置。

性能验收：

- 使用同机 Release，分别测无设备主窗口显示、窗口关闭后菜单栏空闲、菜单操作后恢复空闲；每种稳定状态采样至少 60 秒，重复 3 次。
- 留存 CPU 累计时间差、RSS 原始数据；可用时另测 physical footprint。记录测量环境与工具限制。
- 模拟设备列表只能说明界面开销；真实 HID 查询与蓝牙子进程成本等待设备恢复后独立测量。
- 在改动前后用相同条件对比，调查超过采样噪声的回归；不预设未经测量的 CPU / 内存承诺。
- 发现初始化、整个 CLI 生命周期与 GUI 首帧耗时分别记录。没有可靠首帧测量工具时，保留“未测”。

交付物：可保存设置、精简菜单栏、性能报告、登录项实现与独立验收状态、可运行 0.9.2。登录重启测试未完成时，不把此项列为已验证。

## 6. 0.10.x：扩大适配前，统一证据与操作状态

**用户收益：** 设备是否能读、当前读到了什么、是否只是系统缓存会更清楚；增加新型号时也更容易控制影响范围。

分两次小交付实施，先统一数据，再调整请求管理，避免一次替换所有已验证路径。

任务：

1. 建立静态适配说明，记录 adapter ID、VID/PID、连接方式、接口条件、支持的读/写操作、固定来源 revision 与验证记录。
2. 保持“型号目录”和“可执行适配器”独立；目录中的相似名称或相邻 PID 不自动获得指令能力。
3. 将适配成熟度与当前会话状态分开。前者描述只有资料、模拟通过或哪些硬件组合实测；后者描述未读、读取中、有值、部分失败、连接失效。
4. 每项读数保留来源、取得时间和有效性；电量 0%、未知值、旧值与失败不能相互替代。USB `bcdDevice` 不冒充真实固件版本。
5. 将重复的请求 token、接口指纹、忙碌互斥与断连失效收敛到小型操作协调组件。先迁移一个只读功能，验证后再迁移其余；DPI 写入许可继续独立。
6. 保留现有物理 I/O 串行策略。只有证明收益和线程安全后才考虑按设备并发；避免为了性能引入响应串线。
7. 明确取消语义：未开始的请求可取消，过期结果可丢弃；已进入同步 IOKit 的调用不能承诺立刻终止。遇到持续阻塞时再评估异步 API 或隔离方案，不默认引入常驻辅助进程。
8. 增加可读诊断摘要：枚举成功但无适配器、接口不匹配、权限失败、设备拒绝、协议不一致、系统没有电量数据。观察到官方驱动不等于已证实冲突。
9. 目录增加设备类别、连接参考和适配状态筛选，展示依据；搜索命中型号仍不宣称其所有功能受支持。

验收：

- 同一设备快速重复点击、不同功能竞争、请求中断连、同 PID 重连、睡眠恢复、晚到结果均不会污染当前会话。
- 同型号不同设备不串读、不串写；本地档案的型号级归属与操作时的会话身份仍分别处理。
- 未知型号、错误接口及模拟模式不能进入真实写入路径。
- 迁移前后现有协议字节、响应校验和 DPI 单次确认语义不变；相关协议与竞态测试通过。
- UI、CLI、诊断 JSON 对同一次读取给出一致结果；schema 变化有解码/导出回归记录。

交付物：适配证据表、能力状态模型、逐步收敛的请求管理、回归测试和当前兼容性页面。

## 7. 0.11.x：真机验证与真实功能扩展

这一阶段按设备和功能逐项发布，不用一个“支持 Razer”开关概括全部功能。

| 优先级 | 功能 | 开始条件 | 完成条件 |
| --- | --- | --- | --- |
| P0 | Viper 充电状态、BlackWidow 电池/充电 | 对应硬件可连接，接口符合已审查条件 | 真实读取、异常反馈、正常键鼠输入及断连后恢复有记录 |
| P0 | 现有功能长期稳定性 | 对应设备可用 | 热插拔、鼠标开关、睡眠唤醒、同型号多设备分别验收；无法获取的场景明确保留待验 |
| P1 | 单一型号灯光亮度读取与设置 | 精确型号、接口、命令和响应有公开证据；先确认读取可行 | 用户确认具体值后执行一次设置，能读回则验证读回，视觉效果另记录；影响是否持久化如实说明 |
| P1 | Viper 回报率设置或 DPI 档位切换 | 找到该型号的设置证据与完整校验方法 | 明确确认、设置和独立读回；不能从已实现的查询指令反推设置命令 |
| P2 | 更多 USB / 2.4GHz 型号 | 有公开实现且能获取对应设备样本 | 每个 PID + 连接方式独立报告，至少一个实际功能验收后再宣称该功能可用 |
| P2 | 更多蓝牙电量来源 | macOS 可取得可验证来源，并可准确绑定目标设备 | 不按名称猜测；标准 GATT 路线先验证系统可访问性和身份关联，再考虑实现 |
| 后续专题 | 按键映射、功能键、宏 | 明确硬件映射协议或完成系统事件处理与权限设计 | 先证明单个功能可用及撤销/退出行为，再扩展；与硬件配置的语义分别显示 |

新增控制功能统一交付顺序：固定协议依据 → 请求/响应与坏报文测试 → 手动只读验证 → 准备具体变更 → 用户确认 → 单次写入 → 读回/实际效果验收。

真机测试不自动重试设置、不自动回滚，不进行固件更新。每次可能修改板载存储的动作都按原始要求获得具体确认；过往一次 DPI 写入授权不能用于新动作。

首个灯光功能优先选择可由固件保持的亮度或单色效果。波浪、呼吸等需各自协议证据；暂不安排持续逐帧推送的自定义灯效。按键映射与宏不会与这一阶段捆绑发布。

## 8. 1.0：可安装、可诊断、支持范围明确

任务与门槛：

- 整理版本、构建号、变更记录、实际兼容表和问题报告模板；模板默认不要求序列号、蓝牙地址或原始输入数据。
- 生成真实独立 `.app` 分发产物，验证解压/复制到稳定目录后的启动、资源、签名与升级；发布包不能依赖开发机缓存链接。
- 准备 Developer ID 签名、Hardened Runtime、`notarytool` 公证及 stapling 流程。需要开发者凭据及发布时的网络；运行时仍保持本地工作。[Apple 分发说明](https://developer.apple.com/developer-id/)
- 在干净账户与可获得的其他 macOS 版本验证；最低部署目标不等于实测支持。Intel 如无测试环境，明确未验证，不虚报兼容。
- 在可用的官方软件共存环境记录读取结果与输入是否正常；不自动停止服务或卸载驱动。
- 完成档案升级、损坏数据保护、取消写入和错误恢复回归；保留上一版本安装包作为人工回退选项。
- 首版采用手动更新；自动更新、云同步、账号和遥测不进入这一发布范围。

## 9. 开源参考的具体用法

| 参考 | 采用方向 | 本项目边界 |
| --- | --- | --- |
| FerrisPulse 已审查 revision | 型号识别、读取来源和状态展示的比较；持续参考已有审查记录 | 不将其默认数值、宽泛探测或 Windows 接口当成 macOS 成功证据；本轮没有重新确认远端最新 revision |
| libratbag / Piper | 统一能力接口与具体硬件后端分离、配置管理结构 | 保留 Swift 原生核心，不引入 Linux DBus 服务栈 |
| OpenRazer | 精确 PID、报文字段、功能实现及公开问题中的设备证据 | Linux 内核模块无法直接作为 macOS 驱动复用；逐型号审查和验证 |
| Apple 官方框架 | SwiftUI/AppKit、IOKit、ServiceManagement、签名与分发流程 | 采用公开 API；新增权限仅在相应功能确有需要时引导 |

libratbag 的官方架构将通用 API 与硬件后端分开，可作为静态适配注册和能力模型的参考。[项目架构](https://github.com/libratbag/libratbag#libratbag-internal-architecture) OpenRazer 的官方介绍明确其 Linux 内核模块、守护进程及库分层，可参考协议与设备资料。[项目说明](https://openrazer.github.io/)

FerrisPulse 的固定版本审查见 [FERRISPULSE_REVIEW.md](FERRISPULSE_REVIEW.md)；已有协议证据集中在 [research-sources.json](research-sources.json)。新增参考先记录 revision 和许可证，再决定是否复用代码或仅独立实现公开协议。

## 10. 每次交付的完成定义

1. 只完成一个可说明、可回退的小阶段；代码、界面、诊断和文档对功能状态保持一致。
2. 运行与改动相关的测试及现有回归；完成 Release 构建与签名检查。纯文档变更无需重复构建。
3. 交付可运行产物、测试结果、验证范围和已知限制。模拟报文、组件截图、真实窗口交互与真机通信分别记录。
4. 涉及界面时检查真实交互；涉及协议时保留固定证据、失败测试与真机验收状态。
5. 不把历史一次成功推广到其他连接方式、固件或全部型号，不用无意义的测试数量或估算性能代替验收。

**建议下一范围：0.10.x 适配证据与只读诊断。** 先整理后端的身份条件、协议来源及硬件验证状态，再统一未知型号的诊断导出与能力展示。无外设时完成固定报文和失败路径，硬件查询验收独立保留；同时补测已安装副本的登录重启和状态栏菜单交互。
