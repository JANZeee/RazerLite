# 0.13.0：键盘基础操作与验收记录

日期：2026-11-10。本版包含实时亮度操作、电量与充电查询、回报率配置读取与确认设置。

## 目标与范围

本轮将 Reclusa Mini 65% 的常用操作缩短为：拖动亮度条即可调整，打开设备总览或设置时按需读取电量和配置，选择回报率后一次确认应用。继续使用原生 SwiftUI 和已有串行 HID 执行队列，不引入网络服务、第三方运行时或后台高频轮询。

新增控制路线严格限定为以下已观测的 USB 接收器：

- VID/PID：`1532:02F5`，名称 `Razer Reclusa Mini 65%`。
- 所有组合接口必须属于同一个非虚拟 USB 设备，具有一致的 VID/PID、名称和 USB 身份；组合中必须存在键盘用途接口。
- 唯一控制接口为 USB interface 3，主要用途 `0x0C/0x01`，Input/Output report 长度均为 0，Feature report 长度为 90。
- 复用 `ReclusaLightingAdapter` 的精确匹配规则，不因名称相似、同一厂商或相邻 PID 放开命令。

官方产品包声明 wired product 756 / `02F4`、dongle 757 / `02F5`、BLE 758 / `02F6`。这一身份对应关系不等于所有连接方式均已在 RazerLite 验证：本轮不开放 `02F4`、`02F6`，也不将新协议套用到 BlackWidow、Viper 或其他键盘。既有 Viper 回报率路线及其可写档位保留。

## 亮度条的直接操作

用户已经明确要求拖动即调整；这一操作本身是针对亮度修改的授权，因此新亮度面板移除逐次“检查变更 → 确认”步骤。回报率仍保留具体目标的一次确认。

`LiveBrightnessController` 只接收当前界面的显式编辑：

1. 第一笔编辑先等待 150 ms，合并短时间内的连续输入。
2. 后续操作开始时间至少相隔 250 ms；持续拖动时定期提交最新值，不必等到整个拖动结束。
3. 执行期间最多保留一个最新待处理值，旧值被覆盖；拖回正在执行的目标时取消更早的待处理值。
4. 串行完成当前事务，再处理最新目标。250 ms 是最小间隔，不是硬件响应耗时或性能指标。
5. 空闲时没有定时器或设备轮询；没有持久化的待写入目标，也不会在重连后重放滑块操作。

每个实际执行的目标都经过 `ReclusaLiveBrightnessService`：

- 验证精确设备路线、0–100% 范围以及短期、一次性的操作许可。
- 先读取唯一灯区和 profile 1 当前亮度；已有值等于目标时直接结束，不发送 SET。
- 不同时仅发送一次 SET，严格校验 ACK，随后独立读取同一灯区亮度并比较原始值。
- 对 busy 只有限次继续接收，不重发原命令。写入后断开、ACK 不匹配或读回失败均显示状态未确定，不自动重试、恢复旧值或继续处理排队目标。

百分比编码保持与此前已验证路线一致：写入 `floor(percent × 255 / 100)`，显示按原始值向上换算；例如 50% 对应原始值 127。SET 使用 profile 1、全部灯区 selector 0；读回使用此前确认的具体灯区。

离开灯光面板、切换设备、设备会话变化、断连或系统挂起时，清除待处理目标并撤销操作许可。已开始的物理 I/O 仍占用设备操作锁直到返回，避免后续操作与其重叠；取消不能撤回已经提交给设备的 SET。旧会话的完成结果不得覆盖新会话状态。

## 电量与充电状态

公开官方中间件明确使用带 battery ID 的两字节电源查询，非 BLE 路线的 battery ID 为 0：

| 功能 | Class / Command ID | Data size | 请求参数 | 响应参数 |
| --- | --- | --- | --- | --- |
| 电量 GET | `07:80` | 2 | `[0, 0]` | `[batteryID, rawLevel]` |
| 充电状态 GET | `07:84` | 2 | `[0, 0]` | `[batteryID, chargingState]` |

电量换算为 `floor(rawLevel × 100 / 255)`，有效空电量 0 与读取失败必须分开表示。两种查询独立成功或失败；充电状态成功不能代替电量数据。

官方共享充电枚举包括 0–6，但没有证据表明此键盘固件会返回每一种状态。本轮只将 0 映射为未充电、1 映射为充电中，其他字节保留未知状态。尤其不能把 0 的官方枚举名 `NoCharge_BatteryFull` 当作电量 100%，也不能将任意非零值都转换为充电中。

请求使用 DualLink 键盘事务范围 `80–9E`，电源服务在这个范围内递增并回绕。BLE 官方路径会先查电池列表再选 ID，因此未将 battery ID 0 推广到 BLE。

## 回报率读取与修改

官方接收器路线使用 USB high-speed polling 命令，与其他共享方法中的普通 polling period 格式分开：

| 功能 | Class / Command ID | Data size | 请求参数 | 响应参数 |
| --- | --- | --- | --- | --- |
| 回报率 GET | `00:C0` | 2 | `[1, 0]` | `[profileID, rateCode]` |
| 回报率 SET | `00:40` | 2 | `[1, rateCode]` | `[profileID, rateCode]` |

| 配置频率 | rateCode | 本轮读取 | 本轮写入 |
| --- | --- | --- | --- |
| 125 Hz | `40` | 支持解码 | 开放 |
| 250 Hz | `20` | 支持解码 | 开放 |
| 500 Hz | `10` | 支持解码 | 开放 |
| 1000 Hz | `08` | 支持解码 | 开放 |
| 2000 Hz | `04` | 支持解码 | 暂不开放 |
| 4000 Hz | `02` | 支持解码 | 暂不开放 |
| 8000 Hz | `01` | 支持解码 | 暂不开放 |

官方产品配置启用了高回报率，但运行逻辑还会检查 DualLink 共享连接状态以及特定的高回报率主设备条件，条件不满足时将大于 1000 Hz 的目标降为 1000 Hz。当前工具没有完整验证这一共享连接判定，因此首版只开放不超过 1000 Hz 的写入。较高档位是工具暂未开放，不能表述为硬件不支持。

未知 code 被拒绝；不采用官方通用解析器将未知值默认解释为 8000 Hz 的行为。读取的是设备的配置值，不是对实际 USB 输入事件频率的测量。

界面选择档位后，服务先 GET 当前值，再展示目标与当前值的一次确认。确认计划 60 秒内有效且只能使用一次。执行时重新 GET 检查基线；设备设置已变化、计划取消、会话变化或过期则不发送 SET。Reclusa 应用过程使用 fresh GET `80`、SET `81`、独立 readback GET `82`，严格检查 profile 1、目标 code 和事务号。

本轮只修改 profile 1，不复制官方应用可能执行的其他板载槽位同步。跨重启、断电和硬件切换配置后的持久化语义尚未验证，按可能保存到设备的设置处理。ACK 或读回异常时不重试 SET、不回滚；应重新读取后再决定下一步。

## 读取时机和错误处理

设备枚举和热插拔本身仍不发送未知厂商命令。打开设备总览或对应设置页面时，针对本会话缺少的数据按需读取一次；已有结果可复用，并保留手动刷新。页面不建立周期性电量、亮度或回报率轮询。

读写仍通过共享的串行 HID 执行器和设备操作协调器，不捕获键盘输入接口、不修改系统保护机制，也不运行官方应用的初始化、配对、驱动模式或板载恢复流程。

所有新报文使用已有 90 字节协议封装：核对长度、XOR 校验、协议/分包/保留字段、事务号、命令类、命令 ID、成功状态和负载长度，再校验 battery/profile ID。busy 有接收次数上限；无响应、权限失败、设备断开、拒绝命令和格式错误保留不同错误信息，不将旧值当成新读取成功。
