# 0.3.0：DPI 变更确认与读回

本次实现 Viper V4 Pro `1532:00E6` 指定 USB 接口的 DPI 设置流程。**已在用户明确授权后完成一次本机真实 DPI 写入，并通过应用内完整读回与独立 CLI 查询验证；重启持久性及其他设备/固件尚未验证。** 原有电量/DPI 查询继续可用，键盘、RGB、回报率及其他 PID 的写入未开放。

## 使用方式

1. 运行 `./scripts/test.sh` 和 `./scripts/build-app.sh`，打开 `build/RazerLite.app`。
2. 选择 Viper V4 Pro → 性能，在下方输入目标 X/Y DPI；输入范围 100–50000，步进 50。
3. 点击“检查变更…”。此步**只查询**当前档位表，不设置设备。
4. 查看设备名称、当前档位，以及全部档位的前后对照。取消不会设置设备。
5. 只有明确点击“确认写入设备”才进入设置流程。确认计划 60 秒有效，不能重复使用。确认按钮没有默认回车快捷键。
6. 写入前重新读取档位表；若任何档位或当前档位已变化则中止。写入后重新读取完整表，全部匹配才报告已验证。

读回成功仅证明本次响应与目标一致，不能证明重启后的持久性、所有固件或长期稳定性。收到不匹配/错误、断连等情况会停止，不会自动重发设置或回滚。设置请求可能已到达设备但读回失败时，结果为“未验证”，不能声称没有改变；此时可手动读取最新状态。

## 协议与影响范围

依据 [OpenMouse 精确型号适配器固定版本](https://github.com/OpenMouse-Project/mouse-protocol/blob/54c68c69bbd0bcd750cf10a4e439148e634c02db/src/drivers/razer/viper-v4-pro-hid.ts) 中的 `writeDpi`：90 字节 Feature Report、ID 0、transaction 1F、class/command `04/06`，payload size `3 + 7 × 档位数`。

参数头为 `01 / 一基当前档位 / 档位数`；每档是零基索引、X/Y 大端数值及两个零保留字节。**第一字节使用公开实现的存储标志 1，不能保证临时生效，可能保存到设备。** 本工具不试验另一个存储标志，也没有另行发送“保存”或固件命令。

逻辑上只替换当前档位的 X/Y，底层实际提交完整档位表。已读取的其他档位数值原样保留，包括 2846、49999 等不符合新输入步进的数值。读取响应的索引必须是连续一基、每档保留字段必须为零，否则拒绝准备写入，避免重建报文时丢失未知字段。没有重新配置档位数、切换当前档位或额外的初始化写入。

## 执行边界

- 打开前检查 registry ID、USB 父节点、VID/PID、transport、接口号、usage、长度、版本属性；不独占标准键鼠输入接口。
- 读取、准备及设置使用同一串行执行队列；不会在启动、热插拔、刷新、导入或 CLI 中自动设置。
- 计划绑定设备接口，取消、断连、停止服务、系统将睡眠时失效；设置发送前再次检查单次许可。
- 已提交的 USB 请求无法撤回。取消/睡眠通知与实际 I/O 仍存在系统调度边界；不能承诺中途取消能恢复设备。停止后迟到结果不会用于新连接。
- 官方软件可与本进程并发访问；写前读和写之间没有跨进程原子锁。可能存在其他程序同时改表的竞争，前后校验降低误报，不能彻底消除竞争；不会自动停止官方软件。
- 沿用手动读取已实测的 35 ms 等待与最多 16 次忙碌接收。同步 IOKit 调用的单次超时由 OS/驱动决定，没有虚构整个操作的硬超时。
- 所有计划只在内存中，不持久化或重放。查询、设置结果按当前会话显示，只有用户主动导出时才保存 JSON。

诊断 JSON 继续使用 schema 2，新字段 `dpiWriteResults` 为可选增量，包含 `attemptedWrite`、`outcome`、时间、读回值和消息。操作意图也反映在 `mode` 中；准备阶段的查询不能标为纯发现。不能从没有结果推断设置尚未发生，尤其是应用退出或设备断开时。

## 真机验证授权边界

需要用户明确指定本次要修改的 X/Y DPI 并确认上述设备存储影响，或由用户亲自在确认页点击写入。按原始执行规则，宽泛的“继续开发”不被当成任意目标值/板载修改授权。

获授权后：先准备实际设备当前表，检查差异，只提交一次已确认目标，再读取验证完整表；保存诊断及实测结论。若失败，保留不确定状态，请用户决定是否重读或恢复，不自动执行第二次写入。配置文件管理、RGB 和键盘控制继续另行分阶段实现。

## 本机读取布局与公开抓包复核

初次检查错误地要求 GET 响应也采用零基索引，本机返回 `1,2,3,4,5`，每档保留字段均为零，因此被拒绝，未进入设置。随后审查 [OpenRazer #2760 的原始抓包说明与附件](https://github.com/openrazer/openrazer/issues/2760#issuecomment-4933462400)，发现明确的读写不对称：GET 是一基索引，SET 是零基索引。

下载归档 SHA256 为 `746a881e02604cab1145ca6cbe1c7165720a102cb7bd62aad17b867dd9fc3411`，14 个过滤文件全部匹配附件的 SHA256SUMS；进一步检索有线档位及无线配置 pcap 中 CRC 有效的 90 字节报文，分别确认 GET/SET 的索引基准。回归测试保留一条公开 GET 响应，未把它称为本机设置验证。实现现分别验证读取格式、生成设置格式，而非忽略索引检查。

最终 Release 原生窗口已验证：非法步进阻止提交；输入 2800/2800 后只读准备成功，确认页显示第 3 档 2846/2846 → 2800/2800、其余四档不变；点击取消后仍显示设备原值 2846/2846。没有点击确认写入。初次布局拒绝和后续修正均保留在测试/调研记录中。
