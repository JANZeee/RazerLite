# 0.4.0：本地 DPI 档案

0.9.1 已增加独立离线档案库，支持手动创建、重命名/编辑、复制、导入预览和多接收器载入；格式继续为 schema 1。当前行为与验收范围见 [0.9.1 说明](PHASE091_LOCAL_LIBRARY.md)。以下保留初版设计背景。

本版先实现可审查的“本地 DPI 预设”，不把它称作板载 profile，也不会模仿雷云在后台自动下发设置。它借鉴了 [libratbag](https://github.com/libratbag/libratbag) 将设备能力、profile 和传输后端分开的结构，以及 [Polychromatic](https://github.com/polychromatic/polychromatic) 对版本化配置导入的做法；没有复制、链接或依赖这些项目的代码、资产或运行时。许可边界与此前调研相同：libratbag 为 MIT，Polychromatic 为 GPL-3.0，OpenMouse 的相关协议实现为 AGPL-3.0。

## 现在能做什么

仅对当前已审查的 Viper V4 Pro `1532:00E6` USB 查询接口：

1. 手动读取设备状态后，从当前活动档的 X/Y DPI 创建一个命名预设。
2. 在“档案”页或菜单栏选择预设。
3. 将预设 X/Y 值载入“性能”页的输入框。
4. 导入、导出、删除本地 JSON 预设。

从档案中选择值不会调用 `MouseDPIService.prepare` 或 `apply`，不会打开 HID 传输，也不会自动在启动、热插拔、睡眠唤醒、导入或菜单栏选择后恢复设备。若要实际修改 DPI，仍须由用户手动点击“检查变更…”，检查当前设备完整 DPI 表，再单击确认页的“确认写入设备”；原有单次许可、60 秒有效期、写前重读与整表读回校验继续生效。

预设只存 X/Y 目标值，并不存活动档位或完整五档表。现有真机验证只覆盖“替换当前活动档 X/Y、提交整表、读回整表”的路径，未验证任意切换活动档或把一整套板载状态当作完整 profile。因此档案不会假装具备板载 profile、RGB、按钮、宏、轮询率或自动恢复能力。

## 匹配与隐私边界

档案目标是固定的 `viper-v4-pro-dpi + VID 0x1532 + PID 0x00E6 + USB`。它故意不保存下列字段：

- `DeviceInfo.id`、IORegistry ID 或 USB 父节点；它们是连接会话身份，重连后可能改变。
- 序列号、位置 ID、固件猜测值、输入事件、HID 写入许可或历史写入结果。

这意味着不同的同型号 USB 接收器会共享“上次选择的本地预设”。在有经过验证、可持久读取的硬件身份之前，应用不会声称按物理单件设备分别绑定。蓝牙、相邻 PID、虚拟 HID 或接口布局不满足严格匹配时，不显示可用档案页。

## 文件格式与容错

本地库默认位于：

```text
~/Library/Application Support/RazerLite/profiles.json
```

首次真正保存时才创建目录和文件。写入使用单文件 Codable JSON、ISO-8601 时间与原子替换。导出文件另用 `schemaVersion: 1` 包装预设列表，不携带本地选中状态或任何 HID 会话数据。导入会验证 schema、目标型号、名称、DPI 范围和 50 DPI 步进；相同内容跳过，ID 冲突且内容不同则作为新的本地副本加入，绝不覆盖既有预设。

如果已有本地库损坏或 schema 未支持，应用保留原文件并显示错误，拒绝后续保存/导入，避免把未知用户数据悄悄覆盖为空库。用户可在设置页看到精确存储路径并自行备份或修复。

## 验证范围

新增核心测试覆盖：稳定兼容目标不包含会话 ID、非法名称/DPI 拒绝、保存后重新加载、选择与删除清理、导出导入去重/ID 冲突、未来 schema/错误目标拒绝，以及损坏本地文件不被覆盖。档案服务不依赖 `DeviceManager`、`HIDFeatureTransport` 或 `MouseDPIControlling`，因此从结构上不存在由本地档案操作发起的 HID 写入路径。

原生窗口已人工验证：读取当前 Viper 状态后保存一个本地 2800/2800 预设，选择“载入编辑器”后性能页显示 X/Y 2800；未点击“检查变更…”或“确认写入设备”。这只验证本地档案 UI 与读取结果衔接，不是新的设备设置验证。
